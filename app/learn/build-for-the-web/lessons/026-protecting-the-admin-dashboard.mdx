## Introduction 🧭

- In Lesson 25, the system learned how to:
  - build an Admin Dashboard
  - organize administrative routes
  - create a shared Admin Layout
  - separate Dashboard, Users, Messages, Profiles, and Settings
  - provide administrators with application management tools

```text
Admin Layout

↓

Dashboard

Users

Messages

Profiles

Settings
```

#### Important

```text
The application now
has administrative tools
```

#### But another application problem now appears.

#### The Problem

Right now, anyone can visit

```text
/admin

/admin/users

/admin/messages

/admin/profiles

/admin/settings
```

#### Reality

```text
The application currently
protects nothing
inside the Admin area
```

#### But imagine our application grows.

```text
Peter
  → Administrator

Jane
  → User

John
  → User

Mary
  → User

David
  → User

...
```

#### Question

Who should manage the application?

#### Example

```text
Manage Users

Manage Messages

Manage Profiles
```

#### Problem

```text
Administrative tools
must be protected
```

> Applications are not only concerned with what exists;
> they are also concerned with who is allowed to access it.

- We are still not building:
  - enterprise security policies
  - role hierarchies
  - complex permission systems

- We are building:

```text
Our first Authorization System
```

> This lesson is about protecting the Admin Dashboard and controlling who
> is allowed to access and manage the application's resources.

## Step 1: Protect the Admin Area from Anonymous Visitors 🔐

```text
/admin
```

and access


#### Question

Should anonymous visitors be able to manage the application?

#### Answer

```text
No
```

#### Desired Experience

Anonymous visitors should be redirected to

```text
/login
```

before seeing the Admin Dashboard.

#### Question

Where should this protection live?

#### Reality

All administrative pages already share the same parent.

```text
Admin Layout

↓

Dashboard

Users

Messages

Profiles

Settings
```

#### Therefore

the Admin Layout is a good place to provide the protection.

## Step 2: Introduce Administrators 👮

#### We solved one problem.

Anonymous visitors can no longer access the Admin area.

```text
Anonymous Visitor

↓

Login Page
```

#### But another problem appears.

Consider two authenticated users.

```text
Peter
```

```text
Jane
```

#### Reality

The application currently treats them exactly the same.

```text
Authenticated User

↓

Admin Dashboard
```

#### Question

How can the application distinguish someone who manages the application from
someone who simply uses it?

#### Before we answer that question, let's inspect our application.

#### Open

```text
prisma/schema.prisma
```

#### Observe

The `User` model currently contains

```prisma

	id       String  @id @default(cuid())
	name     String
	username String? @unique
	email    String? @unique
	password String?

	role      String?
	bio       String?
	avatarUrl String?

	messages Message[]
	profile  Profile?
}
```

#### Question

Can we use

```prisma
role
```

to determine who can access the Admin Dashboard?

#### Before deciding, let's see how the application already uses this field.

#### Open

```text
app/routes/home.tsx
```

#### Observe

The profile card displays

```tsx
<p className='text-sm text-slate-500'>{user.role}</p>
```

#### Reality

The existing

```prisma
role
```

field already describes the user's profile.

#### Mental Model

```text
Profile Card

↓

role

↓

Who is this person?
```

Examples

```text
Software Engineer

Teacher

Designer

Lawyer
```

#### But authorization asks a different question.

```text
What is this person allowed to access?
```

#### Therefore

using the same field for both purposes would mix two different responsibilities.

```text
Profile Information

≠

Access Control
```

#### Instead

the application needs a dedicated field for administrative access.

#### Open

```text
prisma/schema.prisma
```

#### Add

```prisma
isAdmin Boolean @default(false)
```

#### The `User` model should now look like

```prisma
model User {
	id       String  @id @default(cuid())
	name     String
	username String? @unique
	email    String? @unique
	password String?

	role      String?
	bio       String?
	avatarUrl String?

	isAdmin Boolean @default(false)

	messages Message[]
	profile  Profile?
}
```

#### Question

Why default to

```text
false
```

#### Answer

Because most users should not automatically become administrators.

Every newly registered user should begin as a regular user unless we
explicitly decide otherwise.

#### Question

Have we finished?

#### Answer

```text
No
```

#### Reality

So far, only the Prisma schema has changed.

```text
Schema

↓

Database

↓

Prisma Client

↓

Application
```

#### Therefore

the database needs to learn about the new field.

#### Run

```bash
npx prisma migrate dev --name add-is-admin-to-user
```

#### Reality

Prisma will

```text
Create a migration

↓

Apply the migration to the database

↓

Usually regenerate the Prisma Client
```

#### However

In practice, there are occasions where the generated Prisma Client does not
immediately reflect the latest schema.

Rather than spending time diagnosing whether the generated client is out of sync,
we'll regenerate it explicitly.

#### Run

```bash
npx prisma generate
```

#### Why?

This guarantees that the generated Prisma Client matches the current Prisma schema.

#### Verify

Open

```text
app/generated/prisma
```

#### Search for

```text
User
```

#### Reality

The generated `User` type should now contain

```ts
isAdmin: boolean
```

#### Compare

Before

```text

↓

Profile Information
```

After

```text
User

↓

Profile Information

↓

Administrative Access
```

The application now has a dedicated place to record whether someone is an
administrator.

```text

```

Every existing user currently has



Our application uses SQLite.





directly.

```tsx
	index('routes/admin/dashboard.tsx'),
	route('users', 'routes/admin/users.tsx', [
		route(':userId', 'routes/admin/users/userDetails.tsx'),
	]),
	route('messages', 'routes/admin/messages.tsx'),
	route('profiles', 'routes/admin/profiles.tsx'),
	route('settings', 'routes/admin/settings.tsx'),
])
```

#### Question

Which route is the parent?

#### Answer

```text
routes/admin.tsx
```

#### Reality

Every administrative page is a child of

```text
routes/admin.tsx
```
